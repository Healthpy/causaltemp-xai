# CausalTemp-XAI: First Full Benchmark Run

**Run date:** 2026-08-17 to 2026-08-18
**Cluster:** PLGrid Helios (Cyfronet), NVIDIA GH200 120GB, `aarch64`
**Code version:** `f4a7f358d55cbfff4bc9db40799055ac4c479485`, branch `run-full-experiments`

**Status.** This first end-to-end run has one defect. Two positive controls fail on the

The `git_dirty` flag is true because of how the code reached the cluster. Git tracks
`results/` and `notebooks/`, but the sync skipped both directories. Git therefore reports
them as deleted. No `.py` file differs from `f4a7f35`. The run records the flag honestly,
but the flag does not show code drift.

Every number in this document comes from one seed. There are no confidence intervals. Do
not read small differences between methods as real effects.

The run excluded `CftsCounts`, so it covers 7 of the 8 methods. The method stays wired in
`build_methods()` at `experiments/03_run_cf_methods.py:106`, and the `--methods` flag
removed it at run time. This method trains a new conditional VAE for each instance. See
`cfts_methods.py:436-451`, which sets `train_epochs=30` and `max_iter=500`. The method needs
2 to 6 hours alone.

A GH200 job built the environment, because the login nodes use `x86_64`. The build pinned
`torch==2.9.0+cu129` from the site wheelhouse. The build did not use the committed
`uv.lock`. That lock file resolves `torch==2.12.0` against CUDA 13. A CUDA 13 build risks a
silent fallback to CPU.

**Threading trap.** The command `module load ML-bundle/25.10` sets `OMP_NUM_THREADS=1`. A
script that then runs `export OMP_NUM_THREADS=$(nproc)` pins itself to one core, because GNU
`nproc` obeys `OMP_NUM_THREADS`. The jobs read `SLURM_CPUS_PER_TASK` instead. Each job also
fails at preflight when `torch.get_num_threads()` is less than 2.

**Split.** `SPLIT_FRACTIONS = (0.6, 0.2, 0.2)`, stratified. See `data_io.py:59`.

**Noise.** The `laplace` setting draws `rng.laplace(loc=0.0, scale=0.1)`. See
`generator.py:327-335`. The code also offers `uniform(-0.17, 0.17)` and
`normal(0, 0.1 * sqrt(2))`, which match the Laplace variance. This run did not use them.

**Label.** The `terminal_threshold` function reads `x[T-1, 0]`, the last timestep of channel
0. See `benchmarks/labels.py:86-99`. It then sets `Y = (latent > median(latent))` across the
population. This median split balances the classes by construction. The code never persists
the threshold.

### Data-generating mechanisms

**Linear family, LinearSCM-T or VAR.** See `generator.py:183-335`.

```
x_t = sum_{l=1..L} A_l . x_{t-l} + eps_t
```

The generator draws coefficients from `U(-0.5, 0.5)`. A Bernoulli(sparsity) graph masks
them. The generator then stabilizes the spectral radius to `target_radius = 0.9`.

**MLP family, NlinearSCM-T.** See `generator.py:338-442` and `mechanisms.py:201-461`.

```
mean_i(history) = decay_i . x_{t-1}^i + gain . tanh(MLP_i(masked lags))
```

Each node has its own 2-layer MLP. The team retuned these values on 2026-08-11 under P0-2.
See `config.py:178-185`.

| parameter | value |
|---|---|
| hidden | 16 |
| gain | 1.5 |
| decay_range | [0.1, 0.4] |
| spectral_cap | 6.0 |
| init_gain | 3.0 |
| activation | tanh |

The initializer sets `std1 = init_gain * sqrt(1/(k*L))` and `std2 = init_gain *
sqrt(1/hidden)`. It then caps each weight matrix at a spectral norm of 6.0. It scales the
inputs by `1/sqrt(max(n_active_parents, 1))`. The divergence guard uses `clip=1e3` and
`max_resample=10`.

**Spring family, SpringSCM-T.** See `generator.py:1015-1176` and `mechanisms.py:463-590`.
The generator uses symplectic Euler integration.

```
accel_i = -sum_j K[i,j] . (x_i - x_j)      K = k_spring . particle_mask
v_t = v_{t-1} + dt . accel
x_t = x_{t-1} + dt . v_{t-1}               (old velocity, symplectic)
```

| parameter | value |
|---|---|
| k_spring | 0.3 |
| dt | 0.1 |
| n_exogenous | 2 (the last 2 particles get no incoming coupling) |

This family has no damping term. Mass stays fixed at 1. The family is not contractive by
design.

**Caveat.** `SpringMechanism.graph` leaves out the position-from-velocity self-coupling on
purpose. The structure-recovery numbers for `smoke_spring` therefore read too low. Do not
compare them against the other families without this note.

### Oracle controls

`experiments/05_run_oracle_control.py` runs two classifier-free positive controls.
`_common.py:613-632` defines the intervention. It sets `ORACLE_SHIFT = 1.5`. For instance
`i` it uses `t0 = T//2`, `node = i % k`, and `value = x[t0, node] + 1.5`.

Both controls call `structural_counterfactual(...)` on the true, known SCM. See
`benchmarks/structural_cf.py:61-102`.

1. **OracleCF-Pearl** runs with `noiseless=False`. It abducts the factual noise
   `eps_t = x_t - f(window)` and reuses it. It is faithful under `pearl_delta` by
   construction.
2. **OracleCF-Rollout** runs with `noiseless=True`. It rolls forward with `eps = 0`. It is
   faithful under `noiseless_rollout` by construction.

Both controls report a blank `validity` by design, because the scorer receives `clf=None`.

## 7. Findings

### 7.1 Both causal positive controls fail on the nonlinear mechanism

This is the main defect of the run. It blocks any reading of the `full_nl` tier.

| config | method | validity | proximity_l1 | frac_degenerate | frac_vacuous | scorable |
|---|---|---|---|---|---|---|
| full_nl | PearlCARLA | 0.000 | 0.0001 | 1.00 | 1.00 | 0/100 |
| full_nl | CARLA | 0.000 | 111.6 | 0.00 | 1.00 | 100/100 |
| smoke_nl | PearlCARLA | 0.000 | 0.0012 | 1.00 | 1.00 | 0/20 |
| smoke_nl | CARLA | 0.000 | 13.7 | 0.00 | 1.00 | 20/20 |

The two methods fail in two different ways. The two flags separate the failures exactly.

**PearlCARLA returns no counterfactual.** It scores `frac_degenerate = 1.00` and
`n_cf_faith_scorable = 0`, with `proximity_l1` near zero. It returned the input almost
unchanged on every instance. CF-faith reads `NaN`, because no post-intervention trajectory
exists to score. This is a bug and not a measurement.

**CARLA edits the trajectory but never flips the label.** It makes real edits, with
`proximity_l1 = 111.6`, `do_complexity = 74`, and 100 of 100 instances scorable. It still
scores `validity = 0.000` and `frac_vacuous = 1.00`. The counterfactual value at the
intervention step equals what the mechanism predicts from its own prefix. No true `do()`
happened anywhere. This matches the known noiseless-rollout pathology at
`scm/intervention.py:157-179`. Dropping the factual noise from `t0` onward inflates
`proximity_l1` and still satisfies rollout-faithfulness.

The mechanism itself works, because the oracle controls behave correctly on the same
`full_nl` data. `OracleCF-Pearl` reaches proximity 24.7 and pearl-faith 1.000.
`OracleCF-Rollout` reaches proximity 83.9 and rollout-faith 1.000. The fault therefore sits
in the CARLA recourse implementations under an MLP mechanism, not in the generator or the
metrics.

The `full_nl` tier has no working causal baseline. Do not report its method ordering as a
result until someone fixes these two methods.

### 7.2 The linear tier reproduces the documented findings

The `full` config at n=100 shows the expected structure.

1. **Do-complexity spans two orders of magnitude.** PearlCARLA scores 0.98, which is about
   one `do()`. TSCausal declares all 100 timesteps as interventions. CftsCOMTE scores 98.7
   and CftsWachter scores 98.3. A method that rewrites the whole trajectory does not explain
   the label.
2. **CF-faith(hard) gives no ranking range.** It reads 0.000 for every method except the
   causal controls. This confirms its documented role as a pass-or-fail admission gate.
   CARLA scores 1.000 rollout and 0.000 pearl. PearlCARLA shows the exact mirror. One
   counterfactual cannot satisfy both semantics at once.
3. **Structure recovery is exact.** SHD is 0, LagAcc is 1.000, LagF1 is 1.000, and
   ResidualDep is 0.002.

### 7.3 Validity and proximity trade off against each other

`CftsCels` reaches `proximity_l1 = 0.29` on `full`, three orders of magnitude tighter than
the 1582 of TSCausal. It still reaches only 0.500 validity, and 47 percent of its
counterfactuals are vacuous. `CftsConfeti` repeats the pattern at 0.560 validity and 44
percent vacuous. Low proximity here partly means that the method changed nothing. Always
read proximity together with `frac_vacuous`.

### 7.4 PearlCARLA validity collapses at full scale

PearlCARLA reaches 0.000 validity on `full` at n=100. It reached 0.800 on `smoke` at n=5 and
T=30. The n=3 profiling job showed the same signal first, and n=100 confirmed it. This is
not sampling noise, and it agrees with the CARLA validity collapse that the team recorded
earlier for long horizons.

## 8. Known limitations

1. One seed for each config, and no confidence intervals. Multi-seed costs 3 times as much.
   The team deferred it to run 2. The command is
   `08_aggregate_and_report.py seeds --seeds 0 1 2`.
2. The `full_nl` tier does not give a valid ranking. See section 7.1.
3. The run did not evaluate `CftsCounts`, because of its cost.
4. Every row carries `git_dirty = true`. Section 1 explains why this is an artifact of the
   file sync.
5. The PNS tables cover the `PS` direction only. The `PN` direction needs `--with-pn`. The
   file `pns.json` records `"PN direction not run"`.
6. The structure metrics for `smoke_spring` read too low by design. See the caveat in
   section 4.
7. The `smoke` rows use n=5 and come from the validation job. Their precision does not match
   the n=100 tiers.
8. `table_axis_c_cf_faith.csv` only appends rows. It holds duplicate `full` rows from the
   profiling job. Deduplicate on `(benchmark, classifier, method)` and keep the last row.
   The `final_table_*.csv` files read from `summary.json` and stay correct.
